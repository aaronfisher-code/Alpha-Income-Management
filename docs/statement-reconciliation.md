# Invoice-first statement reconciliation

The API scans individual invoices and credits, checks them against the existing confidence, supplier and Z-Office amount rules, and automatically enters PDFs that pass. Statements then reconcile those entered values against each statement row. Statements never create invoices or credits and never query Z-Office amounts.

## Flow

1. The Drive worker discovers and classifies PDFs as before. Invoice-folder documents still require `MARKED_OFF`. Statement extraction can run before invoices arrive; reconciliation waits independently.
2. After extraction and invoice/credit amount enrichment, each individual PDF is eligible for automatic entry. Every row in that PDF must pass the existing confidence and 20-cent tolerance checks, resolve to a saved supplier, have a document date, and have a unique reference. Wrong-folder documents, duplicate existing entries, and PDFs with any exception stay in review. A PDF is entered atomically, so one failing row cannot leave it partly saved.
3. The invoice/credit entries and their signed, reviewed values are retained together in `document_invoice_entries`. The immutable Gemini extraction remains separate. Filing to Drive happens after the database commit; retries reuse the retained entry rather than inserting it again. Successfully entered PDFs leave the queue, while the other PDFs in their batch remain available for review.
4. Manual review saves exceptions using the existing workflow. Completion now sends the saved values for every source PDF, including corrected supplier names, references, dates and amounts. If filing failed after automatic entry, the API identifies that PDF as already entered so a reopened desktop review only retries completion.
5. Opening a statement fetches entered scan evidence for its supplier and the count of unfinished supplier invoice documents. A known unfinished invoice for another supplier does not block it. An unidentified queued/failed invoice PDF conservatively blocks reconciliation until its supplier can be established or it is dismissed. Invoice PDFs awaiting `MARKED_OFF` are outside the eligible scanning queue.
6. Statement rows match by supplier, document type and reference. Symbion invoices retain the optional leading `I` alias and leading zeroes. Credits use their own exact references and signed negative amounts. Duplicate statement references or entered documents remain ambiguous; one invoice cannot satisfy two statement rows. Missing references remain missing even after the currently known queue drains, allowing later invoice arrivals to resolve them.
7. The table shows **STATEMENT**, **ENTERED INVOICE**, and **VARIANCE** (entered invoice minus statement). For a uniquely matched row, review lets the accountant edit the entered invoice/credit amount, document date, due date (invoices), and notes. Supplier, reference and document type identify the original entry and remain fixed. The **Show invoice PDF** / **Show credit PDF** button in the PDF preview toolbar switches to the original matched source PDF, including line items and annotations. It changes to **Show statement PDF** to switch back, and keeps draft edits intact. The source is labelled clearly, and statement highlights are cleared while viewing the invoice. Missing or ambiguous matches have no associated invoice action. **Accept invoice changes** retains a draft; **Save statement and invoice changes** commits every drafted edit to its original invoice/credit and updates its retained reconciliation values in the same transaction as statement completion. Amount differences and uncertain extraction can also be acknowledged without changing amounts. Missing, ambiguous and waiting rows cannot be acknowledged. When no invoice values were edited, **Complete reconciliation** completes only the statement batch. The API independently rechecks that every statement row has one entered counterpart and no supplier invoices remain unfinished.

Reopen a waiting statement after invoice review or a later scan to refresh its comparison. The printed statement total versus the extracted statement-row sum remains a separate extraction completeness check.

## Persistence and existing data

The API creates the additive `document_invoice_entries` table at startup. New automatic and manually reviewed entries retain their final values per source document and row. Older completed invoice scans are backfilled when their supplier statement is opened, using the actual saved Alpha invoice/credit values for the scanned references and supplier, never imported Z-Office amounts. Sources that cannot be verified remain missing rather than trusting raw historic extraction. Manually entered records without an independent scanned PDF do not count as scanned evidence.

Statement opening reads the current saved values for independently scanned entries, including ordinary invoice-screen corrections. Accepted edits made during statement review update both the invoice/credit record and its retained entry snapshot on final save; the original Gemini extraction and printed statement rows remain unchanged. Concurrent changes to an edited entry are rejected rather than overwritten, and any failed edit rolls back the entire statement save. A timed-out successful completion is confirmed by checking the batch status before retrying. The statement is limited to its listed references, so additional invoices absent from the statement are not treated as discrepancies.

## Rollout

Deploy the companion **Alpha-API** changes first, restart it to create the new table, and then release the desktop. The new desktop requires `/document-ai/review-batches/{id}/statement-comparison` and `/document-ai/review-batches/{id}/complete-statement`; it deliberately does not fall back to statement-versus-Z-Office reconciliation on an older API. Existing invoice amount lookups and the forwarder need no new endpoint or SQL mapping for this change.

Automatic entry runs in Alpha API without an open desktop. This changes existing qualifying invoice PDFs from review-ready to automatically entered on the next worker run. Existing completion requests without row metadata still file normally; their completed scan evidence can be backfilled from saved Alpha records.
