# Invoice-first statement reconciliation

The API scans individual invoices and credits, checks them against the existing confidence, supplier and Z-Office amount rules, and automatically enters PDFs that pass. Statements then reconcile the current saved Alpha invoice and credit values against each statement row, including older and manually entered records without a linked scan. Statements never create invoices or credits and never query Z-Office amounts.

## Flow

1. The Drive worker discovers and classifies PDFs as before. Invoice-folder documents still require `MARKED_OFF`. Statement extraction can run before invoices arrive; reconciliation waits independently.
2. After extraction and invoice/credit amount enrichment, each individual PDF is eligible for automatic entry. Every row in that PDF must pass the existing confidence and 20-cent tolerance checks, resolve to a saved supplier, have a document date, and have a unique reference. Wrong-folder documents, duplicate existing entries, and PDFs with any exception stay in review. A PDF is entered atomically, so one failing row cannot leave it partly saved.
3. The invoice/credit entries and their signed, reviewed values are retained together in `document_invoice_entries`. The immutable Gemini extraction remains separate. Filing to Drive happens after the database commit; retries reuse the retained entry rather than inserting it again. Successfully entered PDFs leave the queue, while the other PDFs in their batch remain available for review.
4. Manual review saves exceptions using the existing workflow. Completion now sends the saved values for every source PDF, including corrected supplier names, references, dates and amounts. If filing failed after automatic entry, the API identifies that PDF as already entered so a reopened desktop review only retries completion.
5. Opening a statement fetches current saved Alpha invoice and credit records for its supplier and listed references, plus optional scan evidence and the count of unfinished supplier invoice documents. A known unfinished invoice for another supplier does not block it. An unidentified queued/failed invoice PDF conservatively blocks reconciliation until its supplier can be established or it is dismissed. Invoice PDFs awaiting `MARKED_OFF` are outside the eligible scanning queue.
6. Statement rows match by supplier, document type and reference. Invoices use [generic reference alternatives](invoice-reference-matching.md), preserving leading zeros and requiring matching date evidence for automatic fallback acceptance. Credits use their own exact references and signed negative amounts. Duplicate statement references or saved invoice/credit records require review; explicit choices may resolve them only when each statement row uses a distinct saved entry. One invoice cannot satisfy two statement rows. Missing references remain missing even after the currently known queue drains, allowing later invoice arrivals to resolve them.
7. The table shows **STATEMENT**, **ENTERED INVOICE**, and **VARIANCE** (entered invoice minus statement). For a uniquely matched row, review lets the accountant edit the entered invoice/credit amount, document date, due date (invoices), and notes. Supplier, reference and document type identify the original entry and remain fixed. The **Show invoice PDF** / **Show credit PDF** button in the PDF preview toolbar switches to the original matched source PDF when one is linked, including line items and annotations. Saved entries without scan provenance still match and can be edited; the PDF button is disabled and explains that no PDF is linked. It changes to **Show statement PDF** to switch back, and keeps draft edits intact. The source is labelled clearly, and statement highlights are cleared while viewing the invoice. Missing matches have no associated invoice edit action. Reviewing an ambiguous row opens the invoice chooser described below. **Accept invoice changes** retains a draft; **Save statement and invoice changes** commits every drafted edit to its original invoice/credit and updates its retained reconciliation values in the same transaction as statement completion. Amount differences and uncertain extraction can also be acknowledged without changing amounts. Missing, ambiguous and waiting rows cannot be acknowledged. When no invoice values were edited, **Complete reconciliation** saves any selected matches and completes the statement batch. The API independently rechecks that every statement row has one current saved counterpart and no supplier invoices remain unfinished.

Reopen a waiting statement after invoice review or a later scan to refresh its comparison. The printed statement total versus the extracted statement-row sum remains a separate extraction completeness check.

## Choosing an ambiguous invoice

Reviewing an **Ambiguous reference** statement row opens **Choose matching invoice**. The dialog lists eligible saved references for that supplier and document type, including the date, signed saved amount, difference from the statement, source PDF where available and availability. Nothing is preselected. **Use selected invoice** opens the selected entry in the ordinary review form; **Cancel** leaves the row unresolved. The statement's printed reference, date and amount remain its source evidence.

The selected row requires review before completion. Its saved invoice/credit values can be inspected or edited, and a linked PDF can be opened using the existing preview toggle. **Change matched invoice** reopens the chooser. Choosing another entry clears draft invoice edits for that row so edits cannot carry over to a different invoice. Other accepted rows and their edits are preserved.

Each saved entry can satisfy one statement row. Candidates already claimed by another row are unavailable, with an explanation. A repeated extracted statement row with only one saved counterpart remains blocked; check the statement PDF and correct or rescan its extraction. Multiple actual saved records with the same supplier, type and exact reference also remain blocked because selecting a reference cannot distinguish those duplicate records. Distinct eligible reference variants can be chosen explicitly, including for repeated statement references when each is assigned its own saved entry. Pending supplier invoices still block completion.

Choices and edits stay in the current desktop review until **Complete reconciliation** or **Save statement and invoice changes**. Closing and reopening before completion discards these drafts. Final completion sends `StatementCompletion.selections` alongside `edits`. Each selection identifies the statement PDF document ID and row index, its original values and the chosen saved-entry snapshot. Alpha API verifies the row belongs to that statement and store, checks candidate eligibility and uniqueness, locks the current selected invoice/credit and rejects changed amounts, dates or notes. It rechecks the full statement to prevent one saved invoice being used twice. Valid selections are retained in `document_statement_matches` in the same transaction as invoice edits and statement completion; a failure rolls back all three.

## Persistence and existing data

The API creates the additive `document_invoice_entries` table at startup. New automatic and manually reviewed entries retain their final values per source document and row. Older completed invoice scans are backfilled when their supplier statement is opened, using the actual saved Alpha invoice/credit values for the scanned references and supplier, never imported Z-Office amounts. Sources that cannot be verified are not linked to a PDF. Scan evidence is optional: older and manually entered Alpha records still count as entered invoices or credits. Imported Z-Office amounts and raw historic OCR never substitute for saved Alpha values.

Statement opening reads the current saved values directly from `invoices.unitAmount` and `credits.creditAmount`, including ordinary invoice-screen corrections, across months. It loads requested references in chunks of at most 100 per supplier and document type and attaches a unique retained PDF source where available. Multiple scan snapshots do not duplicate one saved entry. Deleted saved entries cannot be matched by stale snapshots. Accepted edits made during statement review update the invoice/credit record and, where linked, its retained entry snapshot on final save; the original Gemini extraction and printed statement rows remain unchanged. Concurrent changes to an edited entry are rejected rather than overwritten, and any failed edit rolls back the entire statement save. A timed-out successful completion is confirmed by checking the batch status before retrying. The statement is limited to its listed references, so additional invoices absent from the statement are not treated as discrepancies.

## Rollout

Deploy and restart **Alpha-API** first, then release the desktop. The API creates the additive `document_statement_matches` audit table at startup for explicit choices. The saved-entry matching and chooser changes use the existing comparison and completion endpoints and require no forwarder update or OCR rescan. Deploy the API supporting `StatementCompletion.selections` before using the updated desktop chooser. Older completion payloads without selections retain their previous behavior. Reopen existing statements after deploying the API to reload their comparisons. The initial invoice-first feature creates its evidence table at API startup. The new desktop requires `/document-ai/review-batches/{id}/statement-comparison` and `/document-ai/review-batches/{id}/complete-statement`; it deliberately does not fall back to statement-versus-Z-Office reconciliation on an older API. Existing invoice amount lookups and the forwarder need no new endpoint or SQL mapping for this change.

Automatic entry runs in Alpha API without an open desktop. This changes existing qualifying invoice PDFs from review-ready to automatically entered on the next worker run. Existing completion requests without row metadata still file normally; their completed scan evidence can be backfilled from saved Alpha records.

The API command runs the document-AI suite rather than the full application-context suite.

## False missing entries fixed in November 2026

Statement comparison previously started exclusively from `document_invoice_entries`, so an invoice visible in the September invoice table could be labelled **Missing entered invoice** when it had no linked scan snapshot. The current-value lookup also filtered scan snapshots by exact statement identity, so generic reference variants could fail to load an editable link or use an outdated snapshot amount. Deleted invoices could incorrectly remain matched through stale snapshots.

A regression fixture reproduces CH2 invoice `73906962`, dated 1 September 2026, due 25 October, with an entered amount of $2,505.37 and the same statement amount. It failed as missing before this fix and now matches without a scan snapshot. The screenshot's imported $2,505.45 belongs to the separate invoice-versus-Z-Office check; statement reconciliation uses the entered $2,505.37. These are local reproductions of the screenshots, not a query of the live store database.

Regression coverage also exercises signed credits, optional PDF links, supplier/store isolation, older invoice dates, deleted records, current amount corrections, reference variants and leading zeros, duplicate saved credits, overlapping lookup chunks, editing several entries without PDFs, concurrent changes and transaction rollback. Desktop tests exercise matching and atomic invoice/credit edits with and without a scanned source.

A follow-up fixture uses CH2 invoice `74399655`, dated 27 October 2026, due 25 November, with a saved and statement amount of $12.23. With one saved invoice and two retained scan records, the old snapshot-based comparison reports **Ambiguous reference**. The updated comparison returns one saved invoice, **Matched**, and $0.00 variance. The PDF link stays unavailable when the two scans cannot be uniquely associated. The user confirmed these screenshots were taken before deploying the API fix; this fixture reproduces a possible cause and does not establish the number of scan records in the live database.
